# Publication and update

All improvements travel through a Pull Request. A publishable candidate contains only accepted optimization changes, directly related regression tests and durable contract or guidance updates. Plans, raw evaluations, conversations, temporary state and other process artifacts remain local and block candidate validation if they enter the Diff.

In `managed` mode, push the approved candidate branch to the verified upstream repository after its dedicated confirmation. In `contribute` mode, validate locally first, then verify and reuse the active account's writable personal Fork or create it through a separate state-bound preview and confirmation. The destination is fixed to `<active-account>/<upstream-name>` and must be a child of upstream. Never merge or release a third-party upstream.

Branch push, PR creation, and later PR updates use different confirmations. PR creation or update requires a branch-push proof bound to the same repository relation, base, branch, candidate commit, and Diff. Before merge, re-read the PR head, checks, ruleset, account, and Diff fingerprint.

Merge is not release. A release requires a SemVer preview, a separate confirmation, and proof that the official tag and GitHub Release contain the approved main commit.

Before the release preview, build a complete inventory from the previous official tag through the candidate commit. Every in-range commit, detected Pull Request, and accepted `OPT-*` must map to a release-note entry or an explicit exclusion reason. Coverage is bound to the candidate commit; incomplete coverage or head drift blocks the preview. Do not summarize only the latest Pull Request.

Only after verified publication may the maintainer offer a local update using the original recorded installation method. A missing or unsafe installation method blocks the update; do not substitute another channel. The current task remains controlled by the old Skill version.

The current Preview provides deterministic apply for personal Fork creation, branch push, PR creation, PR metadata update, merge, and non-draft GitHub Release after a state-bound preview and explicit confirmation. The matching active run must have consumed that approval through its legal lifecycle transition. Apply records a one-time attempt before remote access, so failure or interruption cannot replay the same confirmation. It then re-reads the active account, repository permission, base and head commits, default branch, and relevant Fork, branch, or Pull Request state. If a remote write may have succeeded before output or postcondition reading failed, run the read-only reconcile path. It either recovers the exact Fork, branch, PR, merge, or publication proof, or records the action-specific recovery state. Branch push, PR, merge, and Release may record a state-bound `not_applied` absence proof; only that proof allows the same lifecycle phase to accept a fresh preview and separate confirmation. An unresolved or applied attempt cannot be retried. Commands use argument arrays with interactive prompting disabled; merge never enables admin bypass or auto-merge.

Personal Fork creation first tries a read-only verification of `<active-account>/<upstream-name>`. A valid writable Fork with the expected parent and approved base commit produces Fork proof without a remote write. If the Fork is absent, `fork_create` sends exactly one GitHub request with `default_branch_only=true` after its own confirmation. A second preflight runs after the attempt reservation and immediately before POST; if it fails, record a `not_applied` proof because no remote write began, then require a fresh preview and confirmation after correction. Once POST begins, Fork creation never uses `not_applied`. Because GitHub creates Forks asynchronously, an unobservable Fork, base commit, or uncertain response remains `pending`; reconciliation performs reads only and never repeats the request. An explicit GitHub 4xx refusal is `blocked` and returns a redacted reason instead of being hidden as pending. Five minutes after the recorded attempt an unresolved result becomes `blocked`. Insufficient Fork permission also blocks; wrong owner, parent, repository identity, or a changed upstream relationship is drift, not permission to create another destination. Contributor branch push cannot begin without Fork proof bound to the same account, upstream, destination, base branch, and base commit.

Branch push revalidates the clean committed candidate both before the remote attempt is reserved and again before access. The head branch must differ from the base branch. It creates the named remote branch, advances it only when the approved remote commit is an ancestor, or verifies an existing branch already at the approved commit. Every Git command disables replacement refs and redirects the deprecated graft file to the platform null path, so repository-local graph overrides cannot authorize a history rewrite. The pushed source is the exact approved commit rather than a mutable local branch ref. It uses a temporary isolated Git configuration populated by `gh auth setup-git` and performs remote reads and writes from a clean temporary bare transport repository that exposes only the approved candidate object database; candidate-local URL rewrites, credential helpers, proxies, and other transport configuration are never read. It derives an exact GitHub HTTPS URL from the verified repository and binds the approved remote prestate through `--force-with-lease=<ref>:<expected>` as a compare-and-swap guard. Plain `--force`, an unspecified lease, non-fast-forward updates, forced outcomes, upstream tracking, and reading or modifying candidate remote configuration are prohibited.

Release apply additionally requires Release immutability to be enabled and confirms that neither the requested tag nor Release exists. After creation, verify the official Release metadata and dereferenced tag both point to the approved commit. A failed postcondition is a blocked recovery case, not permission to repeat the same approval.

The apply path does not create organization-owned Forks, choose custom Fork names, synchronize or delete Forks, clean candidate resources, or update the installed Skill. Those capabilities remain unavailable until they have their own deterministic implementation and confirmation contract. Never substitute ad-hoc commands for a missing path.
