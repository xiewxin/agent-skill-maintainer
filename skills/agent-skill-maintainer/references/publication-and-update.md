# Publication and update

All improvements travel through a Pull Request. A publishable candidate contains only accepted optimization changes, directly related regression tests and durable contract or guidance updates. Plans, raw evaluations, conversations, temporary state and other process artifacts remain local and block candidate validation if they enter the Diff.

In `managed` mode, push the approved candidate branch to the verified upstream repository after its dedicated confirmation. In `contribute` mode, validate locally first, then verify and reuse the active account's writable personal Fork or create it through a separate state-bound preview and confirmation. The destination is fixed to `<active-account>/<upstream-name>` and must be a child of upstream. Never merge or release a third-party upstream.

Initial branch push and PR creation may use different confirmations or one exact `publish_pr` confirmation. The compound action contains only those two ordered writes and preserves separate branch and PR proofs. A push-only result cannot replay the compound approval. If PR state is unobservable it remains `pending` and permits only read-only reconcile; only a later read-only absence proof records `partial` and unlocks a fresh granular PR-creation confirmation. Later PR updates always remain separate. Granular PR creation or update requires a branch-push proof bound to the same repository relation, base, branch, candidate commit, and Diff. Before merge, re-read the PR head, checks, ruleset, account, capability proof, and Diff fingerprint.

Merge is not release. Ending after merge requires an explicit `stop_after_merge` disposition plus the verified merge proof. A later `publication-continue` run may resume at merge from that exact terminal proof. The same command may recover a migrated pre-v8 `legacy_completed` run only when its candidate, validation and PR proof are complete and the supplied detached merge proof exactly matches a fresh read-only GitHub observation of the merged PR, including base branch, candidate head and merge commit. Verification happens before a new run or lease; ordinary terminal states, an unmerged PR, incomplete evidence and every mismatch block. Release still requires a fresh SemVer preview, separate confirmation, and proof that the official tag and GitHub Release contain the approved main commit.

Before the release preview, build a complete inventory from the previous official tag through the candidate commit. Every in-range commit, detected Pull Request, and accepted `OPT-*` must map to a release-note entry or an explicit exclusion reason. Coverage is bound to the candidate commit; incomplete coverage or head drift blocks the preview. Do not summarize only the latest Pull Request.

Only after verified publication may the maintainer offer a local update using the original recorded installation method. A missing or unsafe installation method blocks the update; do not substitute another channel. The current task remains controlled by the old Skill version.

The deterministic lifecycle provides read-only GitHub capability inspection and apply for personal Fork creation, branch push, compound `publish_pr`, PR creation, PR metadata update, merge, and non-draft GitHub Release after a state-bound preview and explicit confirmation. The matching active run must have consumed that approval through its legal lifecycle transition. Apply records a one-time attempt before remote access, so failure or interruption cannot replay the same confirmation. It then re-reads the active account, repository permission, base and head commits, default branch, and relevant Fork, branch, or Pull Request state. If a remote write may have succeeded before output or postcondition reading failed, run the read-only reconcile path. It either recovers the exact Fork, branch, PR, compound, merge, or publication proof, or records the action-specific recovery state. Branch push, PR, merge, and Release may record a state-bound `not_applied` absence proof; only that proof allows the same lifecycle phase to accept a fresh preview and separate confirmation. A compound push-only result retains the branch proof but never permits compound replay; unobservable PR state remains `pending`, and only read-only absence proof changes it to the granular-fallback `partial` state. An unresolved or applied attempt cannot be retried. Commands use argument arrays with interactive prompting disabled; merge never enables admin bypass or auto-merge.

Personal Fork creation first tries a read-only verification of `<active-account>/<upstream-name>`. A valid writable Fork with the expected parent and approved base commit produces Fork proof without a remote write. If the Fork is absent, `fork_create` sends exactly one GitHub request with `default_branch_only=true` after its own confirmation. A second preflight runs after the attempt reservation and immediately before POST; if it fails, record a `not_applied` proof because no remote write began, then require a fresh preview and confirmation after correction. Once POST begins, Fork creation never uses `not_applied`. Because GitHub creates Forks asynchronously, an unobservable Fork, base commit, or uncertain response remains `pending`; reconciliation performs reads only and never repeats the request. An explicit GitHub 4xx refusal is `blocked` and returns a redacted reason instead of being hidden as pending. Five minutes after the recorded attempt an unresolved result becomes `blocked`. Insufficient Fork permission also blocks; wrong owner, parent, repository identity, or a changed upstream relationship is drift, not permission to create another destination. Contributor branch push cannot begin without Fork proof bound to the same account, upstream, destination, base branch, and base commit.

Branch push revalidates the clean committed candidate both before the remote attempt is reserved and again before access. The head branch must differ from the base branch. It creates the named remote branch, advances it only when the approved remote commit is an ancestor, or verifies an existing branch already at the approved commit. Every Git command disables replacement refs and redirects the deprecated graft file to the platform null path, so repository-local graph overrides cannot authorize a history rewrite. The pushed source is the exact approved commit rather than a mutable local branch ref. It uses a temporary isolated Git configuration populated by `gh auth setup-git` and performs remote reads and writes from a clean temporary bare transport repository that exposes only the approved candidate object database; candidate-local URL rewrites, credential helpers, proxies, and other transport configuration are never read. It derives an exact GitHub HTTPS URL from the verified repository and binds the approved remote prestate through `--force-with-lease=<ref>:<expected>` as a compare-and-swap guard. Plain `--force`, an unspecified lease, non-fast-forward updates, forced outcomes, upstream tracking, and reading or modifying candidate remote configuration are prohibited.

Release apply additionally requires Release immutability to be enabled and confirms that neither the requested tag nor Release exists. After creation, verify the official Release metadata and dereferenced tag both point to the approved commit. A failed postcondition is a blocked recovery case, not permission to repeat the same approval.

## Deterministic local update

The first supported local-update contract is a global `npx-skills` installation with canonical content at `.agents/skills/<skill>`. Codex uses that canonical directory; Claude Code may use the normal symlink to it. The global v3 lock is read from the installer's standard home location or absolute `XDG_STATE_HOME`; an absolute `CLAUDE_CONFIG_DIR` is honored for Claude Code. The binding must declare `scope=global`, `mode=symlink`, `source_type=github`, the exact GitHub repository and Skill subpath, lock schema v3, selected Agent links, and the canonical-path fingerprint. The live installation, binding, global lock, source, Skill frontmatter name, installed tree, and links must agree before a preview is valid.

The preview binds the active run, binding, repository relation, verified non-draft Release proof, exact Release commit, installed and published tree fingerprints, lock-entry fingerprint, link fingerprint, and operation. Approval is short-lived and valid only for that preview. The lifecycle consumes it before apply and reserves its update fingerprint exactly once before filesystem mutation. GitHub may report a Release `targetCommitish` as a branch name; the authoritative immutable check is that the dereferenced Release tag still resolves to the proof commit.

Apply reads the exact GitHub commit tree and blobs through authenticated GitHub API calls. It never follows a moving branch, tag name alone, or generic “update latest” command. Reject traversal, duplicate or case-colliding paths, unsupported entry modes, symlinks, submodules, special files, oversized trees, invalid blob hashes, and a missing or mismatched `SKILL.md` frontmatter name before touching the installation. Do not execute published files, hooks, installer scripts, or Provider commands.

Materialize verified regular files in a same-parent staging directory, verify its tree fingerprint, and preserve the original lock bytes. Switch the canonical Skill directory with atomic renames, update the v3 lock through an atomic same-parent replacement, advance its `ref` to the exact Release tag, and then revalidate the full installation contract and the live Release tag. Preserve source identity, Skill path, installation time, unrelated entries, and top-level lock metadata. On any failed postcondition, restore both the previous Skill directory and exact original lock bytes. A proven already-applied state returns an update proof without rewriting files. An unprovable rollback is `blocked`; do not claim success or retry the same approval.

If apply output is interrupted or uncertain, reconcile performs reads only. It produces a verified update proof only when the exact Release tree, lock entry, and Agent links are present. Proven unchanged old state is `not_applied`; verified rollback is `rolled_back`; identity or content disagreement is `drifted` or `blocked`. Only `not_applied` or `rolled_back` permits a new preview and explicit confirmation. Proofs and persisted run state contain fingerprints and repository-relative installation identity, never local absolute paths.

Project-scoped, copy-mode, plugin, manual, unknown, or drifted installations are unsupported in this version. The deterministic apply path also does not create organization-owned Forks, choose custom Fork names, synchronize or delete Forks, clean candidate resources, or update the current task's in-memory Skill. Those capabilities remain unavailable until they have their own deterministic implementation and confirmation contract. Never substitute ad-hoc GitHub, filesystem, or installer commands for a missing path.
