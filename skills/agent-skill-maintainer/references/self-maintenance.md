# Self-maintenance

When this Skill is the target, the currently installed stable version remains the controller and the candidate stays in an isolated repository checkout.

The candidate cannot approve its own implementation, PR, merge, release, update, cleanup, or evaluation result. Keep the stable controller as workflow owner. When the candidate introduces a new scorer contract that the installed version cannot parse, lock a separately reviewed neutral controller by source SHA-256 and public key before the held-out sessions start. The corresponding private key must be generated and retained outside the candidate checkout and run directory; neither candidate code nor reusable harness source may contain it. That controller must independently parse the provider transcripts, enforce the locked read-only tool profile, derive the headline result, and sign the exact source/result payload; candidate code may verify the attestation but cannot be its only producer. The same controller must sign each post-unblind platform challenge before its sessions begin and sign the observed completion record only after all four provider processes finish. The challenge has a bounded lifetime and an exact nonce per platform/case; the completion binds actual start/completion times, exit status, provider version/session, and response/transcript hashes, so a candidate cannot prefill completion or turn an old final response into current evidence. Permit at most one self-improvement iteration per invocation.

After an official release is verified, ask whether to update through the original installation method. Do not hot-swap the Skill during the current task; a new task may use the updated version.
